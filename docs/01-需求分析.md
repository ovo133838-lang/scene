## 1. 项目概述

### 1.1 业务背景

一家 Shop 商城销售少量标准商品，运营负责维护商品售价和可售数量，买家通过网页下单并在线支付，仓库人员根据已付款订单发货，客服处理取消、退款和支付异常。业务规模虽小，但一个订单同时影响库存、收款、发货和客服处理，单独显示"支付成功"不能说明订单已正确完成。

本次活动中，某商品只剩 5 件。多名买家同时下单，其中一人迟迟不付款，一人在付款后、仓库发货前要求退款。支付渠道因网络重试重复发送成功通知，另有一笔成功通知在订单超时关闭后才到达。仓库还可能在客服处理退款时点击发货。若系统处理不清，可能出现超卖、重复退款、买家已退款却继续发货，或渠道已收款但商城查不到有效订单等问题。

### 1.2 项目目标

交付一套供买家、仓库、客服、运营共同使用的小型交易系统，达成：

- 买家能明确知道"钱和订单去了哪里"；
- 仓库能明确知道"哪些单可以发"；
- 客服能明确知道"哪些异常需要处理"；
- 运营在活动结束后能核对订单、库存与收退款结果。

### 1.3 项目范围

**范围内（必须实现）**

1. 用户端：商品浏览、下单、支付、订单查询、取消、售前退款申请与结果查询。
2. 后台管理端：多角色（运营 / 仓库 / 客服）RBAC 权限管理，各角色仅可访问其职责内功能。
3. 核心业务闭环：订单 → 支付 → 发货 → 退款/异常处理，全部持久化到 MySQL，服务重启后结果可查。
4. 支付宝沙箱真实支付链路 + 可控支付通知网关（用于触发题面要求的异常通知场景）。
5. 接口级鉴权：所有按钮操作与接口访问均须通过 JWT 身份认证与角色/资源级授权。

**范围外（本题不实现）**

- 购物车、多商户、优惠券、运费、积分、会员。
- 完整财务系统、发票、对账单。
- 签收、退货、售后物流、部分退款。
- 注册登录完整流程（账号可预置），真实短信通知（站内消息即可）。
- 微服务拆分、真实第三方生产环境接入（支付宝沙箱为测试环境，非生产接入）。

### 1.4 术语与缩写

| 术语 | 说明 |
| --- | --- |
| 订单占用 | 下单即占用可售数量，未付款释放 |

### 2.3 鉴权要求（硬性）

1. 用户端、后台管理端所有按钮操作与接口调用，在执行业务逻辑前必须完成身份认证（JWT）与角色/资源授权校验。
2. 买家仅能访问、操作本人订单；后台角色仅能访问其权限矩阵内的功能。
3. 禁止通过篡改请求中的用户编号越权操作他人订单（越权场景须有明确拒绝结果）。
4. 服务端必须做资源归属校验，前端隐藏按钮不视为权限控制。

## 3. 业务流程

### 3.1 整体业务流

```text
运营上架商品
   └─▶ 买家浏览商品并下单（占用库存）
            ├─▶ 买家支付成功确认 ──▶ 订单待发货
            │        ├─▶ 仓库发货登记 ──▶ 已发货（买家查询运单）
            │        └─▶ 买家申请售前退款 ──▶ 客服审核
            │                 ├─▶ 同意 ──▶ 渠道退款 ──▶ 退款成功（恢复库存）
            │                 │                  └─▶ 退款失败 ──▶ 客服重试
            │                 └─▶ 拒绝 ──▶ 恢复可发货
            ├─▶ 买家主动取消 ──▶ 释放库存
            ├─▶ 10 分钟未付款 ──▶ 超时关闭 ──▶ 释放库存
            │        └─▶ 收到迟到成功通知 ──▶ 异常支付待处理 ──▶ 客服核实退款（不恢复库存）
            └─▶ 库存不足 ──▶ 下单失败
```

### 3.2 订单状态流转

| 状态 | 编码 | 说明 | 可流转至 |
| --- | --- | --- | --- |
| 待付款 | PENDING_PAYMENT | 下单占用库存，10 分钟有效 | 待发货、已关闭 |
| 待发货 | PAID | 支付成功确认 | 退款申请中、已发货 |
| 退款申请中 | REFUND_PENDING | 买家申请，客服待审核，暂停发货 | 待发货(拒绝)、退款处理中(同意) |
| 退款处理中 | REFUND_PROCESSING | 客服同意，渠道退款执行中 | 已退款、退款待重试 |
| 退款待重试 | REFUND_FAILED | 渠道明确失败，保留待处理记录 | 退款处理中 |
| 已退款 | REFUNDED | 退款成功，售前退款恢复库存 | 终态 |
| 已发货 | SHIPPED | 仓库登记发货 | 终态（本题无售后） |
| 已关闭 | CLOSED | 主动取消或超时关闭 | 终态（迟到支付→另生成异常记录，订单不复活） |
| 支付异常 | PAYMENT_ABNORMAL | 关闭后收到成功通知，待客服退款 | 已退款(迟到支付退款，不恢复库存) |

## 5. 业务规则（BR）

### BR-01 商品与下单
1. 买家只能购买在售且数量足够的商品。
2. 订单保存下单时的商品快照与价格，后续上下架、价格调整不改变已有订单金额。
3. 创建订单后，可售数量须反映已占用数量（库存扣减实时生效）。

### BR-02 待付款与超时
1. 待付款订单保留 10 分钟。
2. 买家主动取消或超时关闭后释放占用；重复关闭不多释放。
3. 超时判断采用服务端时间。

### BR-03 支付通知与去重
1. 有效支付通知须通过鉴权、匹配订单及金额。
2. 重复通知不能重复记款。
3. 同一渠道交易号不得归属于两个订单。
4. 金额不符、未知订单、验签失败须可查询处理结果。

### BR-04 迟到支付
1. 订单有效期内收到并校验通过的付款通知，使订单进入待发货。
2. 超时关闭后收到成功支付通知，不能恢复订单、不能重新占用库存，应进入"异常支付待处理"列表，由客服核实后发起退款。

### BR-05 售前退款
1. 买家对已付款未发货订单可申请整单退款，申请期间暂停发货。
2. 客服可同意或拒绝并写明原因；拒绝后允许继续发货。
3. 退款与发货同时发生时，只能形成一种合法业务结果（并发冲突必须确定性收敛）。

### BR-06 退款结果
1. 退款经渠道确认成功后，买家能看到退款结果，正常售前退款恢复相应可售数量。
2. 渠道明确失败时保留待处理记录，由客服重试。
3. **迟到支付对应的退款不得再次恢复此前已释放的数量**（库存已在超时关闭时释放过，不得二次增加）。

### BR-07 发货
1. 仓库只能为合法待发货订单登记一次发货。
2. 已发货订单不受理本题售前退款。
3. 本题不实现签收、退货及售后物流。

### BR-08 运营核查
1. 运营可按订单查询收款、退款、发货和异常处理记录。
2. 查看商品可售数量、已收款及已退款汇总。
3. 异常记录不能通过直接修改订单状态消失（异常处理须走客服退款链路留痕）。

**支付实现要求（硬性）**

1. 可使用支付宝官方 SDK（github.com/smartwalle/alipay/v3 等成熟 Go SDK）或按沙箱开放接口自行实现，均须完成真实支付效果：买家端发起支付 → 沙箱收银台实际付款 → 沙箱异步通知到达服务端。
2. 服务端收到异步通知必须验签（公钥模式），验签通过、订单匹配、金额一致后**真实改变订单状态**（待付款 → 待发货），并落库支付流水。
3. 回调处理须幂等：重复通知不重复记款、不重复改状态。
4. 退款走沙箱退款接口，退款结果回调同样验签并驱动退款单状态。
5. cpolar 隧道地址重启后可能变化，notify_url 须可配置；演示前须核对外网可回调。

### 7.3 通知网关（可控模拟）
- 支付发起：创建支付宝沙箱支付单并返回支付入口。
- 异步通知（真实）：支付宝沙箱 notify_url 回调，服务端验签、匹配订单与金额。
- 通知网关（可控模拟）：提供注入成功/失败/超时/重复/迟到/验签失败/金额不符/未知订单等通知的入口，用于异常场景演示与测试。
- 退款接口：发起退款并接收退款结果回调。

## 8. 非功能需求（NFR）

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 一致性 | 库存、收款、退款、发货四者强一致；并发下单不超卖、重复通知不重复记款、退款与发货并发唯一收敛 |

| NFR-04 | 性能 | 支持 20 并发下单争抢场景，库存扣减无超卖 |
| NFR-05 | 可测试性 | 单元测试整体与核心包覆盖率 ≥85%；并发场景可重复执行验证 |
| NFR-06 | 可追溯 | 订单、支付、退款、发货全链路留痕，状态变更不可跳变抹除 |

## 10. 验收标准（AC）

### 10.1 完整工作场景（须逐项可演示）

| 场景 | 步骤 | 预期结果 |
| --- | --- | --- |
| AC-01 正常成交 | 运营上架 → 买家购买付款 → 仓库发货 → 买家查运单 → 运营核查收款与库存 | 全链路闭环，金额与库存一致 |
| AC-02 缺货与弃单 | 20 个并发下单抢 5 件 → 部分未付款关闭 → 其他买家购买释放商品 | 无超卖；超时释放后可被再购 |
| AC-03 售前退款 | 买家付款后申请 → 仓库发货受限 → 客服批准 → 首次退款失败、再次成功 → 订单与数量恢复一致 | 退款成功恢复库存，首次失败有重试记录 |
| AC-04 迟到支付 | 订单先关闭 → 支付成功通知到达 → 客服异常列表发现 → 发起退款 → 运营确认无重复释放与重复退款 | 不复活订单、不二次恢复库存、不重复退款 |
| AC-05 操作竞争 | 退款申请与发货并发、重复支付/退款通知、越权访问 | 唯一合法结果；越权明确拒绝 |
